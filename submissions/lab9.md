### RPO answer

With one manual `pg_dump`, the RPO is equal to the age of the latest dump at the moment of failure. Any committed changes after that dump may be lost.

In this run, the dump was only a few seconds old, so the observed gap was 2 orders. Scheduled backups reduce the maximum loss window. For an RPO measured in seconds rather than minutes, continuous WAL archiving / PITR is more appropriate than occasional logical dumps.

### Why was the replacement Postgres pod empty?

Before the Bonus change, PostgreSQL stored PGDATA only inside the container writable layer. Deleting the pod removed that storage, so the replacement container initialized a fresh empty database.

A PersistentVolumeClaim moves PGDATA outside the pod lifecycle and prevents data loss caused only by pod recreation.

## Bonus - Persistent Storage and Automated Backup

### PersistentVolumeClaim

I added a `postgres-data` PVC, mounted it at `/var/lib/postgresql/data`, set `PGDATA` to the `pgdata` subdirectory, and used `strategy: Recreate` so the old PostgreSQL pod is removed before the replacement uses the same RWO volume.

```text
$ kubectl get pvc postgres-data

```

### Automated backup CronJob

The CronJob runs every five minutes, uses `concurrencyPolicy: Forbid`, writes PostgreSQL custom-format dumps to the provided backup PVC, and keeps the five newest dump files.

### Backup design notes

The CronJob first writes to a `.partial` file and renames it only after `pg_dump` succeeds. This avoids treating an incomplete dump as a valid backup.

Retention sorts by the UTC timestamp embedded in the file name and removes everything older than the five newest dumps.
