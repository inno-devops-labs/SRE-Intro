## Introduction

The objective of this lab was to explore database reliability in Kubernetes. I worked with Alembic database migrations, performed backup and restore operations using PostgreSQL tools, measured Recovery Time Objective (RTO) and Recovery Point Objective (RPO), and improved database reliability by introducing persistent storage and automated backups.

# Task 1 — Database Migrations and Backup/Restore

## 1.1 Alembic Setup

Alembic was initialized and configured for the QuickTicket database.

Commands executed:

```bash
alembic init migrations
alembic revision -m "baseline - pre-existing schema"
alembic stamp head
```

### Verification

The migration history was verified using:

```bash
alembic history
```

The output confirmed that the baseline revision had been successfully created.

---

## 1.2 Database Migration Under Load

A new migration was created to add an `email` column to the `events` table.

Migration:

```python
def upgrade():
    op.add_column(
        'events',
        sa.Column('email', sa.String(255), nullable=True)
    )
```

While the migration was running, the application continued serving requests generated by the mixed load deployment.

Migration execution:

```bash
time alembic upgrade head
```

### Observations

* The migration completed successfully in approximately **0.8 seconds**.
* No noticeable increase in application errors was observed during the migration.
* Because the new column was nullable, the schema change did not interrupt normal application operation.

### Verification

The updated schema was verified using:

```bash
kubectl exec -i $(kubectl get pod -l app=postgres -o name) -- \
psql -U quickticket -d quickticket -c '\d events'
```

The new `email` column appeared as `character varying(255)` and accepted `NULL` values.

## 1.3 Database Backup and Restore

### Creating a Backup

A compressed PostgreSQL backup was created using:

```bash
kubectl exec -i $(kubectl get pod -l app=postgres -o name) -- \
pg_dump -U quickticket -Fc quickticket > /tmp/quickticket.dump
```

### Backup Verification

The backup file was verified using:

```bash
ls -lh /tmp/quickticket.dump

kubectl exec $(kubectl get pod -l app=postgres -o name | cut -d/ -f2) -- \
pg_restore --list /tmp/backup.dump | head -15
```

The backup file was created successfully and contained the expected database objects.

### Simulating Data Loss

To simulate a disaster, the `orders` table was removed:

```sql
DROP TABLE orders CASCADE;
```

### Database Restore

The database was restored from the backup:

```bash
kubectl exec $POD -- \
pg_restore -U quickticket -d quickticket \
--clean --if-exists /tmp/backup.dump
```

### Verification

Database recovery was verified by checking the table contents before and after restoration.

```text
Before disaster:
SELECT count(*) FROM orders;

After DROP:
SELECT count(*) FROM orders;

After restore:
SELECT count(*) FROM orders;
```

After the restore completed, the API responded successfully and normal application functionality was restored.

### Recovery Point Objective (RPO)

The experiment demonstrated that the Recovery Point Objective depends on the time elapsed since the most recent backup. Any data written after the latest backup would be lost during disaster recovery.

# Task 2 — Disaster Recovery Under Load

## Failure Scenario

To simulate a database failure, the PostgreSQL pod was forcibly deleted.

```bash
kubectl delete pod -l app=postgres --grace-period=0 --force
```

Kubernetes automatically recreated the pod.

Because PostgreSQL was using ephemeral storage, the recreated pod started with an empty database.

The backup was restored and the Events service was restarted to reconnect to the recovered database.

### Recovery Timeline

* PostgreSQL pod deleted.
* Replacement pod created automatically.
* Database restored from backup.
* Events deployment restarted.
* Application returned to normal operation.

### Recovery Objectives

* **Recovery Time Objective (RTO):** approximately **2 minutes**, including pod recreation, database restoration, and application restart.
* **Recovery Point Objective (RPO):** limited by the age of the latest backup. Any changes made after the backup would not be recovered.

During the recovery process, monitoring showed a temporary increase in application errors until the database became available again.

### Conclusion

This experiment demonstrated that running PostgreSQL without persistent storage creates a significant risk of data loss after pod recreation. While backups enable recovery, they also increase recovery time and may result in data loss between backup intervals.

# Bonus Task — Persistent Storage and Automated Backups

## Persistent Storage

To improve database reliability, a PersistentVolumeClaim (PVC) with **1 GiB** of storage was added to the PostgreSQL deployment.

After introducing persistent storage, recreating the PostgreSQL pod no longer caused data loss. Existing database files remained available after the pod restarted, eliminating the need for manual restoration during normal pod failures.

As a result, recovery time was reduced to approximately the PostgreSQL startup time.

---

## Automated Backups

A Kubernetes CronJob was created to automate database backups.

Configuration:

* Backup interval: every **5 minutes**
* Retention policy: keep the **five most recent** backup files

Verification commands:

```bash
kubectl get cronjob postgres-backup
kubectl get jobs
kubectl exec deployment/backup-inspector -- ls -lh /backups/
```

The automated backup process successfully created backup files according to the configured schedule while enforcing the retention policy.

# Final Conclusion

This lab demonstrated the importance of reliable database management for stateful applications running in Kubernetes.

The main concepts explored included:

* Database schema migrations using Alembic
* Performing migrations while the application remains available
* Creating and restoring PostgreSQL backups
* Measuring Recovery Time Objective (RTO) and Recovery Point Objective (RPO)
* Protecting database data with PersistentVolumeClaims
* Automating backups with Kubernetes CronJobs

The most important lesson learned is that production databases should always use persistent storage together with regular automated backups. Combining these techniques significantly improves application reliability and minimizes both recovery time and potential data loss during failures.
