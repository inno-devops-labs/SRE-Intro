### 3. Top 3 risks + fixes.
Evaluating the system limits exposed by the 10/50/100 user load tests and historical failure modes, here are the top 3 structural risks to stability and their alignment strategies:

#### Risk 1: Gateway and Compute Saturation under Load (Breaking Point)
* **Impact:** High load (50+ users) causes cascading connection drops on the ingress gateways, flooding the client with `502 Bad Gateway` errors and triggering `500` codes downstream. 
* **Engineering Fix:** Implement a **Horizontal Pod Autoscaler (HPA)** for the gateway and backend microservices based on target CPU/Memory utilization thresholds. Pair this with definitive cluster autoscaling and explicit `resources.requests` optimizations to guarantee predictable pod scheduling loops under spike traffic.

#### Risk 2: Ephemeral Database Storage Lifecycle (Mitigated)
* **Impact:** Complete data wipeout and long MTTR (~66 seconds) upon any unexpected PostgreSQL container eviction or host node migration due to lack of detached storage.
* **Engineering Fix:** Transitioned the deployment into a stateful layer by anchoring the container directory (`/var/lib/postgresql/data`) to a **PersistentVolumeClaim (PVC)** backed by a local storage class. This decoupled storage lifecycle from the container runtime, driving RTO down to **6 seconds** without data loss.

#### Risk 3: Cache Single Point of Failure (Redis Saturation)
* **Impact:** If Redis crashes or experiences network isolation, ticket reservations fail instantly. Additionally, if the cache memory limits are reached, the database faces an unbuffered thundering-herd problem.
* **Engineering Fix:** Deploy **Redis Sentinel** or a replicated Redis Cluster configuration within the cluster to eliminate the single point of failure. Introduce a **Circuit Breaker** pattern (e.g., using Resilience4j or native gateway filters) to gracefully gracefully degrade service functionality instead of dropping client traffic when cache lookups stall.

### 5. Monitoring-gap list.
Reviewing the data from the Lab 8 chaos experiments and the combined failure scenarios, the following critical visibility gaps were identified in our Prometheus setup:

* **What was missing during Chaos Experiments:**
  * **Telemetry Blindness on Total Failure:** During the latency injection (Experiment 2) and the combined outage scenario, core metrics like `/events/{id}/reserve` and `/health` resolved to **`NaN`** (Not a Number), and the `/pay` endpoint **completely vanished** from the active scraped telemetry loops. Because the monitoring system only gathered data from *successful* or *completed* request loops, we became entirely blind to the system's state precisely when it was collapsing.
  * **Lack of Internal Saturation Metrics:** We were forced to infer database connection exhaustion purely from the gateway's edge `502 Bad Gateway` error rates. We lacked direct tracking of internal application resource saturation (such as active thread pools, database connection pool utilization, or Redis memory buffers).

* **Alerts that would have caught the structural failures:**
  * **Metric Absence Alert (Dead-Man Switch):** An alert using the `absent()` function or checking for zero transaction rates on critical checkout paths:
    `sum(rate(gateway_requests_total{path="/pay"}[2m])) == 0`
    *Why:* This would instantly trigger a high-priority PagerDuty page if a core business route suddenly stops receiving traffic due to an upstream block.
  * **Database Pool Saturation Alert:** An internal application metric alert triggering when connection utilization crosses a safe threshold:
    `(database_open_connections / database_max_connections) > 0.85`
    *Why:* This would have warned us about the database connection starvation *before* it caused a cascading 100% failure rate across the platform.

### 6. Capacity plan.
Based on the empirical breaking-point boundaries discovered during the 10/50/100 user load-testing matrix, the infrastructure requires structural scaling to sustain future business growth.

* **Current Capacity Ceiling:**
  The current maximum safe ceiling for the platform is **15 to 20 RPS**. While the system successfully handles **7.63 RPS** at 10 users, it completely violates the reliability SLO at 50 users (**36.01 RPS**), where the error rate jumps to 2.09% and tail latency reaches 490 ms.

* **For 2× Traffic (Target: Safe Handling of ~70–80 Peak RPS), we must scale:**
  * **Gateway Deployment:** Increase replicas from 5 to **8 pods** to handle aggregate network socket distribution.
  * **Events Microservice:** Scale from 1 to **3 pods** controlled by a Horizontal Pod Autoscaler (HPA) targeting 70% CPU utilization.
  * **Payments Microservice:** Scale from 1 to **3 pods** to prevent latency bottlenecks from locking synchronous request threads.
  * **Database Client Scaling:** With 3 `events` pods running at the fixed Lab 8 patch of `DB_MAX_CONNS=30`, the backend PostgreSQL instance must be reconfigured to support `max_connections = 120` (allocating a 90-connection pool for compute nodes + overhead for administrative access).

* **Rough Cost Estimate:**
  * *Current Local/Cloud Footprint:* ~1.5 Cores CPU, 3 GiB RAM (Equivalent to roughly $40–$50/month on standard cloud compute options like AWS t3.medium nodes).
  * *Proposed 2x Scaled Architecture:* ~4.5 Cores CPU, 8 GiB RAM. This requires shifting the node pool to higher capacity general-purpose instances (e.g., 2x m5.large instances or equivalent), bringing the estimated infrastructure expenditure to approximately **$110–$130/month**. This is a reasonable 2.5x cost tradeoff to guarantee 100% business availability under high concurrency stress.

### 8. Detailed capacity plan with replica counts, resource limits, cost.
To safely sustain a permanent 2× increase in peak transaction volume (~70–80 peak RPS) while remaining strictly within our reliability SLO boundaries, the cluster architecture must scale according to the following mathematical model:

#### 1. Target Replica Provisioning
* **Gateway Layer:** Increase from 5 to **6 replicas** (provides an $N+1$ safety buffer for high network socket load distribution).
* **Events Service:** Scale horizontally from 1 to **3 replicas** to distribute core processing and eliminate the primary 88m CPU constraint.
* **Payments Service:** Scale from 1 to **2 replicas** to guarantee high availability once the upstream bottlenecks are resolved and payment traffic flows smoothly.

#### 2. Standardized Resource Allocations
To avoid CPU throttling and unpredictable container eviction loops, explicit hardware guarantees are assigned based on empirical telemetry limits:
* **Gateway Pods:** `requests: 50m` / `limits: 100m` (safely encloses the observed 49m peak).
* **Events Pods:** `requests: 100m` / `limits: 200m` (insulates the core logic engine with growth headroom).
* **Payments Pods:** `requests: 20m` / `limits: 50m` (provides minimal overhead for handling real downstream requests).

#### 3. Stateful Infrastructure Adjustments
* **Cache Layer (Redis):** From a raw compute standpoint, a single-pod Redis setup is still technically sufficient to handle 80 RPS. However, to mitigate catastrophic data-loss risks highlighted in Lab 8, a **replicated Redis setup (Redis Sentinel)** is recommended for production environments.
* **Database Layer (PostgreSQL):** Running 3 parallel instances of the `events` service with the Lab 8 tuning parameter of `DB_MAX_CONNS=30` will demand up to **90 simultaneous connections**. The single-pooler-to-single-Postgres path *will* become a bottleneck. 
  * *Mitigation:* The backend Postgres resource must be scaled to support `max_connections = 120` in its deployment manifest, or an active proxy like **PgBouncer** must be introduced.
