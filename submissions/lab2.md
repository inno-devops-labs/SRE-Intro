### 2.6 Written answer — Docker DNS service discovery

**How does the gateway find the events service? What IP does `events` resolve to?**

`events` resolves to `172.19.0.5`. The resolution happens through Docker's embedded
DNS server, which listens at `127.0.0.11` inside every container on the same
Compose network (this is what `/etc/resolv.conf` inside the gateway points to —
not the host's own DNS, a resolver that Docker itself runs per-network). Compose
registers each container's service name against that resolver when it starts, so
any container on `app_default` can look up `events`, `payments`, or `gateway` by
name and get back the current container IP for that service.

I confirmed this isn't just a resolver returning a plausible answer — it's the
real address traffic uses. The same IP (`172.19.0.5`) shows up in three independent
places: `docker inspect app-events-1`, `docker network inspect app_default`, and
`socket.gethostbyname('events')` run from inside the gateway. And the events
access log for the reserve request shows the client IP as `172.19.0.6`, which is
the gateway's own container IP — so the request genuinely traveled over that
address, it wasn't just resolved and then routed some other way.

The reason this matters operationally: the gateway's config references services
by name (`events:8081`, `payments:8082`), never by IP. Container IPs aren't
stable — if a container gets recreated (rebuild, restart, scale), it can come
back with a different address on the bridge network. Service names are stable
across all of that, so name-based discovery is what keeps `docker-compose.yaml`
and the app code from needing to change every time a container restarts.

## Bonus Task — Trace a Request Across Services

Cleared logs (`docker compose down && docker compose up -d`), waited for healthy, then ran
one full purchase flow. Reservation `36e92e9c-eaf8-4842-b3ab-ebe53e08f33b`, pay returned
`200 {"...","status":"confirmed"}`.

Full timestamped trace (`docker compose logs --timestamps`, infra/startup noise removed,
sorted by container timestamp):

```
2026-09-14T15:37:52.311238553Z | events   | Reserved 1 tickets for event 1: 36e92e9c…      (events: reserve work done)
2026-09-14T15:37:52.312235303Z | events   | POST /events/1/reserve 200                       (events -> gateway)
2026-09-14T15:37:52.313079011Z | gateway  | HTTP Request: POST events:8081/events/1/reserve 200  (gateway got reserve resp)
2026-09-14T15:37:52.314227345Z | gateway  | POST /events/1/reserve 200  -> client            (gateway returns reserve)

2026-09-14T15:37:52.392185553Z | payments | Payment success: PAY-DAE1F06C for 36e92e9c…      (payments: charge done)
2026-09-14T15:37:52.392773720Z | payments | POST /charge 200                                 (payments -> gateway)
2026-09-14T15:37:52.393616928Z | gateway  | HTTP Request: POST payments:8082/charge 200       (gateway got charge resp)
2026-09-14T15:37:52.400634803Z | events   | Order confirmed: 36e92e9c…                        (events: DB insert done)
2026-09-14T15:37:52.401022636Z | events   | POST /reservations/36e92e9c…/confirm 200          (events -> gateway)
2026-09-14T15:37:52.401782970Z | gateway  | HTTP Request: POST events:8081/reservations/36e92e9c…/confirm 200  (gateway got confirm)
2026-09-14T15:37:52.402924928Z | gateway  | POST /reserve/36e92e9c…/pay 200  -> client        (gateway returns pay)
```

Per-hop deltas (container timestamps, ms):

| From → To | Δ (ms) |
|---|---|
| events reserve work → events returns 200 | 0.997 |
| events returns → gateway got reserve resp | 0.844 |
| gateway got resp → gateway returns reserve to client | 1.148 |
| **RESERVE call total (in logs)** | **2.989** |
| payments charge done → payments returns 200 | 0.588 |
| payments returns → gateway got charge resp | 0.843 |
| gateway got charge → events confirm (DB insert) done | 7.018 |
| events confirm done → events returns 200 | 0.388 |
| events returns → gateway got confirm resp | 0.760 |
| gateway got confirm → gateway returns pay to client | 1.142 |
| **PAY span in logs (payments charge done → pay 200 to client)** | **10.739** |

Raw facts for the end-to-end answer:
- Both `PAYMENT_FAILURE_RATE` and `PAYMENT_LATENCY_MS` were `0` for this run (payments env, 2.2).
- Individual hops are all sub-millisecond except the **confirm/DB-insert step (~7 ms)**, the
  single most expensive hop in the pay path.
- The gateway logs request **completion**, not receipt, so there is no explicit "gateway
  received pay" line; the earliest pay-path log is payments finishing the charge.
- The ~78 ms between the reserve `200` and the payments charge is **inter-curl scripting
  latency** (reserve returns → bash runs `python3` to parse the RID → pay curl fires), not
  a service-to-service hop — do not count it as request latency.

**What is the total end-to-end time from gateway receiving the request to
returning the response?**

Being precise about what's actually measurable: the gateway doesn't log the
moment it *receives* the pay request, only the moment each downstream call
completes. So I can't read a true "request received → response sent" number
directly off these logs — the earliest pay-path log line is payments finishing
the charge, not the gateway accepting the call. What I can measure honestly is
the internal service tail: from the moment payments finishes charging to the
moment the gateway returns the response to the client, which is about **10.7 ms**
(reserve itself, separately, completes in about 3 ms end-to-end).

Within that 10.7 ms pay span, almost all of it is one hop: the confirm step,
where events writes the order into Postgres, takes about 7 ms — everything else
(the HTTP round-trips between gateway/payments/events) is sub-millisecond. So if
this were a real system and I had to pick one thing to optimize, it would be the
Postgres insert on confirm, not the network calls — the network here is basically
free, the database write is the actual cost.

One more thing worth flagging: the ~78 ms gap between the reserve response and
the payments charge starting is not part of the system's latency at all — it's
the delay in my own test script between issuing the reserve curl, parsing the
reservation ID in bash, and firing the pay curl. In a real client this gap
wouldn't exist (or would be whatever the actual client's own processing time is),
so it shouldn't be read as something QuickTicket itself is slow at.
