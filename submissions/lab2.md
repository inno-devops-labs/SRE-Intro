2.5 — Network inspection

```bash
docker network ls | grep app
docker network inspect app_default --format '{{range .Containers}}{{.Name}}: {{.IPv4Address}}{{"\n"}}{{end}}'
```
Output:
```
2cae62c3e762   app_default   bridge    local

app-postgres-1: 172.22.0.4/16
app-gateway-1: 172.22.0.6/16
app-redis-1: 172.22.0.2/16
app-payments-1: 172.22.0.3/16
app-events-1: 172.22.0.5/16
```

**Answer — How does the gateway find the events service? What IP does `events` resolve to?**
All five containers sit on the same user-defined bridge network `app_default`. Docker Compose registers each container's service name in the embedded DNS server at `127.0.0.11` (visible in `gateway`'s `/etc/resolv.conf`), so when gateway's code calls `http://events:8081`, that DNS server resolves `events` to the container's current IP on `app_default` — `172.22.0.5` — without any hardcoded IPs or extra service-discovery infrastructure. This is why the mapping still works after a container restart even though Compose can assign it a new IP: the name `events` always resolves to whatever IP that container currently has.

## Bonus Task — Trace a Request Across Services

Setup:
```bash
docker compose down && docker compose up -d
sleep 5
RES=$(curl -s -X POST http://localhost:3080/events/1/reserve \
  -H "Content-Type: application/json" -d '{"quantity":1}')
RES_ID=$(echo "$RES" | python3 -c "import sys,json; print(json.load(sys.stdin)['reservation_id'])")
curl -s -X POST "http://localhost:3080/reserve/$RES_ID/pay"
docker compose logs --timestamps
```
Response:
```
{"reservation_id":"280fed36-1ffd-41ce-a8ca-482b834a6470","event_id":1,"quantity":1,"total_cents":5000,"expires_in_seconds":300}
{"order_id":"280fed36-1ffd-41ce-a8ca-482b834a6470","event_id":1,"quantity":1,"total_cents":5000,"status":"confirmed"}
```

Full timestamped logs for this reservation (`280fed36-1ffd-41ce-a8ca-482b834a6470`), filtered from `docker compose logs --timestamps`, in chronological order with annotations:

```
[1] events-1   2026-09-13T17:24:12.295584914Z  "Reserved 1 tickets for event 1: 280fed36..."
    → events: reservation written to Redis + DB read complete, about to respond to gateway

[2] events-1   2026-09-13T17:24:12.297221077Z  POST /events/1/reserve → 200 OK
    → events: HTTP response sent back to gateway                              (+1.6ms since [1])

[3] gateway-1  2026-09-13T17:24:12.299280820Z  HTTP Request: POST events:8081/events/1/reserve "200 OK"
    → gateway: httpx client received the response from events                 (+2.1ms since [2])

[4] gateway-1  2026-09-13T17:24:12.301375397Z  POST /events/1/reserve → 200 OK
    → gateway: response returned to the client — RESERVE call complete        (+2.1ms since [3])

    ── reserve leg total: [1] → [4] = 5.8ms ──

    (client parses reservation_id, issues the /pay request)

[5] payments-1 2026-09-13T17:24:12.393552591Z  "Payment success: PAY-5C708EFC for 280fed36..."
    → payments: charge processed (PAYMENT_LATENCY_MS=0, so this fires almost
      immediately after gateway's POST /charge arrives)

[6] payments-1 2026-09-13T17:24:12.394362122Z  POST /charge → 200 OK
    → payments: HTTP response sent back to gateway                            (+0.8ms since [5])

[7] gateway-1  2026-09-13T17:24:12.395839713Z  HTTP Request: POST payments:8082/charge "200 OK"
    → gateway: httpx client received the charge confirmation                  (+1.5ms since [6])

[8] events-1   2026-09-13T17:24:12.409259185Z  "Order confirmed: 280fed36..."
    → events: gateway's confirm call landed, order INSERTed into postgres,
      Redis reservation key deleted                                          (+13.4ms since [7])

[9] events-1   2026-09-13T17:24:12.411491115Z  POST /reservations/{id}/confirm → 200 OK
    → events: HTTP response sent back to gateway                              (+2.2ms since [8])

[10] gateway-1 2026-09-13T17:24:12.413699922Z  HTTP Request: POST events:8081/reservations/.../confirm "200 OK"
    → gateway: httpx client received the confirm response                     (+2.2ms since [9])

[11] gateway-1 2026-09-13T17:24:12.416332871Z  POST /reserve/{id}/pay → 200 OK
    → gateway: final response returned to the client — PAY call complete      (+2.6ms since [10])

    ── pay leg (charge → confirm → response): [5] → [11] = 22.8ms ──
```

Trace summary — the request hops through all 3 services in the expected order for a full purchase:
`gateway → events (reserve)` → `gateway → payments (charge)` → `gateway → events (confirm)` → back to the client.

**Answer — total end-to-end time:**
- The **reserve** call ([1]→[4]) takes ~5.8ms end-to-end (gateway → events → gateway, single hop).
- The **pay** call is the interesting multi-service leg: from payments finishing the charge ([5]) to gateway returning the final response ([11]) is **~22.8ms**, made up of a payments round trip (~2.3ms) plus an events-confirm round trip (~17.8ms, dominated by the postgres `INSERT INTO orders` at [8]) plus final response overhead (~2.6ms). There is no explicit "gateway received POST /pay" log line emitted by the app, so this is measured from the first internal side-effect of the handler (the payments charge succeeding) rather than the raw inbound request — the true wall-clock time as seen by the client would be a few hundred microseconds longer to account for the initial gateway → payments network hop not captured in any log line.
