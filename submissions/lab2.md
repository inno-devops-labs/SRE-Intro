**How many layers?** 15 layers (before the Task 2 non-root-user change, 17 after, see Task 2).

**Which layer is largest, and why?**
The single largest layer is the base `debian.sh` rootfs layer at **87.6MB**, that's the Debian
`trixie` base filesystem that `python:3.13-slim` is built from (libc, coreutils, apt, etc.), so
it's not something we control. Among the layers *our* Dockerfile actually adds, the largest is
**`RUN pip install --no-cache-dir -r requirements.txt` at 43.9MB**. That's where FastAPI, uvicorn,
httpx, asyncpg/redis clients and their transitive dependencies land. The `apt-get install
dpkg-dev g++ gcc gnupg libbluetooth-dev ...` build-toolchain layer baked into the slim base comes
close behind at 40.4MB, followed by the ca-certificates/tzdata layer at 4.95MB. Our own `COPY` layers
(`main.py`, `requirements.txt`) are tiny (12–20KB) since the app code itself is small.

### 2.6 — How does the gateway find the `events` service? What IP does `events` resolve to?

Compose puts every service in the stack on one user-defined bridge network (`app_default`), and
Docker runs an embedded DNS server at `127.0.0.11` inside every container on that network (visible in
`/etc/resolv.conf` above). When the gateway code calls `http://events:8081/...`
(`EVENTS_URL=http://events:8081` from `app/docker-compose.yaml`), the container's libc resolver sends
the query to `127.0.0.11`, which looks up the service name `events` in Docker's internal DNS records
for that network and returns the container's IP on `app_default`, **`172.19.0.5`** (confirmed by both
`docker inspect app-events-1` and `docker network inspect app_default` above). There's no hard-coded
IP or `/etc/hosts` entry involved. This also means the IP can change across container recreation
(compare `172.19.0.5` here) and the app still works, because it resolves the name fresh each call.

whatever junk was actually in the build context, and here there wasn't any. The file is still
good practice for when those files do show up, e.g. a local `.git` clone or `__pycache__` left
over from running tests.

### 2.8 — Non-root user

Added to all three Dockerfiles before `CMD`:

```dockerfile
RUN addgroup --system app && adduser --system --ingroup app app
USER app
```

Rebuilt with `docker compose up -d --build`; all 5 containers came back `Up`/`healthy`.

```

$ docker exec app-events-1 whoami
```

## Bonus Task — Trace a Request Across Services

Stack was cycled clean (`docker compose down && docker compose up -d`), 5s wait, then a full
reserve → pay flow was executed:

```
$ RES=$(curl -s -X POST http://localhost:3080/events/1/reserve \
    -H "Content-Type: application/json" -d '{"quantity":1}')
$ echo "$RES"
{"reservation_id":"ba6d762d-6736-4c3d-8969-2a1472b0fdbf","event_id":1,"quantity":1,"total_cents":5000,"expires_in_seconds":300}
$ RES_ID=$(echo "$RES" | python3 -c "import sys,json; print(json.load(sys.stdin)['reservation_id'])")
$ curl -s -X POST "http://localhost:3080/reserve/$RES_ID/pay"
{"order_id":"ba6d762d-6736-4c3d-8969-2a1472b0fdbf","event_id":1,"quantity":1,"total_cents":5000,"status":"confirmed"}
```

Full timestamped logs (`docker compose logs --timestamps`), filtered to the lines that reference
reservation `ba6d762d-6736-4c3d-8969-2a1472b0fdbf`, in chronological order, annotated:

```
[1] events-1   2026-09-21T20:47:21.034882381Z {"msg":"Reserved 1 tickets for event 1: ba6d762d-..."}
      -> events: RESERVE step. Ticket held in Postgres, TTL set in Redis.

[2] events-1   2026-09-21T20:47:21.035876305Z INFO: 172.19.0.6:33642 - "POST /events/1/reserve HTTP/1.1" 200 OK
      -> events: access log for the reserve call, responds 200 to gateway.        (+0.99ms since [1])

[3] gateway-1  2026-09-21T20:47:21.037047371Z {"msg":"HTTP Request: POST http://events:8081/events/1/reserve \"HTTP/1.1 200 OK\""}
      -> gateway: its outbound httpx client logs the events response it received. (+1.17ms since [2])

[4] gateway-1  2026-09-21T20:47:21.038666773Z INFO: 172.19.0.1:34102 - "POST /events/1/reserve HTTP/1.1" 200 OK
      -> gateway: responds 200 to the original client curl (end of the /reserve call). (+1.62ms since [3])

      --- client parses reservation_id, immediately issues POST /reserve/{id}/pay ---

[5] payments-1 2026-09-21T20:47:21.107228183Z {"msg":"Payment success: PAY-1BA271EE for ba6d762d-..."}
      -> payments: PAY step. Gateway forwarded the pay request to payments' /charge. (+68.56ms since [4],
         includes client-side gap between the two curl calls, not pure service latency)

[6] payments-1 2026-09-21T20:47:21.107773961Z INFO: 172.19.0.6:42062 - "POST /charge HTTP/1.1" 200 OK
      -> payments: access log, responds 200 to gateway.                            (+0.55ms since [5])

[7] gateway-1  2026-09-21T20:47:21.108709757Z {"msg":"HTTP Request: POST http://payments:8082/charge \"HTTP/1.1 200 OK\""}
      -> gateway: httpx client logs the payments response it received.            (+0.94ms since [6])

[8] events-1   2026-09-21T20:47:21.117296432Z {"msg":"Order confirmed: ba6d762d-..."}
      -> events: CONFIRM step. Gateway called events' /reservations/{id}/confirm to finalize the order. (+8.59ms since [7])

[9] events-1   2026-09-21T20:47:21.118005946Z INFO: 172.19.0.6:33642 - "POST /reservations/ba6d762d-.../confirm HTTP/1.1" 200 OK
      -> events: access log, responds 200 to gateway.                              (+0.71ms since [8])

[10] gateway-1 2026-09-21T20:47:21.118720770Z {"msg":"HTTP Request: POST http://events:8081/reservations/ba6d762d-.../confirm \"HTTP/1.1 200 OK\""}
      -> gateway: httpx client logs the events confirm response it received.       (+0.71ms since [9])

[11] gateway-1 2026-09-21T20:47:21.120117897Z INFO: 172.19.0.1:34110 - "POST /reserve/ba6d762d-.../pay HTTP/1.1" 200 OK
      -> gateway: responds 200 to the original client curl (end of the /pay call). (+1.40ms since [10])
```

This confirms the purchase flow is: **gateway → events (reserve)** → *(client)* → **gateway →
payments (charge) → gateway → events (confirm) → gateway → client**. Each hop is visible twice,
once as the receiving service's access log, once as the gateway's outbound `httpx` client log.
That's what let me follow the request purely from `docker compose logs --timestamps` without
any tracing tool.

**Total end-to-end time, gateway receiving `/pay` to gateway returning the response** ([4]→[11],
i.e. excluding the idle gap where the test script parsed JSON between the two curl calls):
payments' internal processing to gateway's final response spans **[5]→[11] = 12.9ms**
(`21.107228183Z` → `21.120117897Z`), which covers payments charge, events confirm, and all
inter-service hops. Since the logs don't capture the exact instant gateway received the `/pay`
HTTP request from curl (only when its downstream calls resolve), this ~13ms is the tightest
lower bound I can get from the logs.

As a direct, independently-measured cross-check, a second reserve+pay was run with `curl -s -o
/dev/null -w "%{time_total}\n"` timing the `/pay` call itself end-to-end from curl's perspective:

```
$ curl -s -o /tmp/pay_resp.json -w "pay_time_total_seconds=%{time_total}\n" \
    -X POST "http://localhost:3080/reserve/$RES_ID2/pay"
pay_time_total_seconds=0.015164
```

**Answer: end-to-end time for the `/pay` request (gateway receiving it, doing payments-charge +
events-confirm, and returning) is ~13–15ms.** This lines up between the log-timestamp analysis
(12.9ms) and the direct curl wall-clock measurement (15.2ms), all running on localhost with no
real network latency.
