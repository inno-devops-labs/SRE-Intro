### How Service Discovery Works

The gateway is configured with `EVENTS_URL=http://events:8081`, so it connects to the service name `events`, not a hard-coded container IP. Docker Compose attaches the containers to `app_default` and makes service names resolvable through Docker's embedded DNS server at `127.0.0.11`. In this run, `events` resolved to `172.19.0.5`, which exactly matches the Events address from both `docker inspect` and `docker network inspect`. Docker may assign a different IP after recreation; the stable service name lets the gateway continue to find the current container.

## Task 2 — Dockerfile Optimization

### `.dockerignore`

The same file was added to `app/gateway`, `app/events`, and `app/payments`:

```dockerignore
__pycache__
*.pyc
.git
.env
*.md
.vscode
```

This excludes caches, local configuration, editor metadata, and documentation from the build context.

### End-to-End Analysis

- The complete log-observable purchase chain, from the first reservation business event to the final gateway response log, took **72.412 ms**.
- For the pay request alone, the observable server chain from the first downstream business event (`Payment success`) to the final gateway response took **5.827 ms**.
- The client measured the whole pay HTTP call at **9.886 ms**.

The exact gateway-receive-to-gateway-response server duration cannot be calculated from the default logs: Uvicorn writes its access record after request handling, and the gateway does not log a request-start timestamp. The logs are sufficient to correlate the flow, but exact server-side end-to-end latency requires request-start instrumentation or distributed tracing. The client timing is useful corroborating evidence, but it is not a substitute for the missing gateway receive timestamp.
