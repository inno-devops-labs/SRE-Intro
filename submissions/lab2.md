### 2.4 Logs analysis

After generating one reservation request, the following related records appeared in the two service logs:

```text
events-1  | {"time":"2026-09-13 14:16:32,908","level":"INFO","service":"events","msg":"Reserved 1 tickets for event 1: 92576944-c34b-4c83-ac42-afd9fe95ed01"}
events-1  | INFO: 172.28.0.6:51872 - "POST /events/1/reserve HTTP/1.1" 200 OK
gateway-1 | {"time":"2026-09-13 14:16:32,923","level":"INFO","service":"gateway","msg":"HTTP Request: POST http://events:8081/events/1/reserve \"HTTP/1.1 200 OK\""}
gateway-1 | INFO: 172.28.0.1:58856 - "POST /events/1/reserve HTTP/1.1" 200 OK
```

Yes, this request can be followed manually across the gateway and events services because the path, status code, source IP, and timestamps match. The events service recorded the reservation at `14:16:32.908`, and the gateway recorded the downstream response at `14:16:32.923`, about 15 ms later. Timestamps alone become ambiguous under concurrent load, so production systems normally add a request ID or trace ID and use distributed tracing.

### 2.6 Docker DNS service discovery

Docker Compose created the user-defined bridge network `app_default` and connected all five containers to it. Docker's embedded DNS server is available inside the gateway at `127.0.0.11`. It resolves a Compose service name to the current container address on that network. Therefore, the gateway can call `http://events:8081` and the name `events` resolves to `172.28.0.5` in this run. The service name is stable even if the container is recreated and receives a different IP address.

The same `.dockerignore` was added to `gateway`, `events`, and `payments`:


Image sizes before and after a no-cache rebuild were:

| Image | Before | After | Difference |
|---|---:|---:|---:|
| `app-events` | 245 MB | 245 MB | 0 MB |
| `app-gateway` | 226 MB | 226 MB | 0 MB |
| `app-payments` | 223 MB | 223 MB | 0 MB |

The sizes did not change at the displayed precision. This is expected because the build contexts were already very small: approximately 1.553 kB, 3.638 kB, and 4.874 kB. `.dockerignore` reduces the build context and prevents accidental inclusion of unwanted files, but it does not reduce the base-image or dependency layers that account for almost all of these image sizes.

### 2.8 Non-root user

Each service Dockerfile was updated before its `CMD` instruction:

```dockerfile
RUN addgroup --system app && adduser --system --ingroup app app
USER app
```

After rebuilding and recreating the containers, the gateway ran as the new unprivileged user:

```text
$ docker exec app-gateway-1 whoami
app
```

This reduces the impact of a container compromise because the application process no longer runs as UID 0 inside the container.

The Dockerfile changes are:

```diff
diff --git a/app/events/Dockerfile b/app/events/Dockerfile
--- a/app/events/Dockerfile
+++ b/app/events/Dockerfile
@@
 EXPOSE 8081
+RUN addgroup --system app && adduser --system --ingroup app app
+USER app
 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8081"]

diff --git a/app/gateway/Dockerfile b/app/gateway/Dockerfile
--- a/app/gateway/Dockerfile
+++ b/app/gateway/Dockerfile
@@
 EXPOSE 8080
+RUN addgroup --system app && adduser --system --ingroup app app
+USER app
 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]

diff --git a/app/payments/Dockerfile b/app/payments/Dockerfile
--- a/app/payments/Dockerfile
```

## Bonus Task — Trace a Request Across Services

The Compose stack was restarted to clear the previous logs. A reservation was created and then paid. The same reservation ID, `a919095b-828a-4bb4-b89a-3077a9e82848`, links the complete trace.

```text
events-1   | 2026-09-13T14:50:40.805769260Z Reserved 1 tickets for event 1: a919095b-828a-4bb4-b89a-3077a9e82848
events-1   | 2026-09-13T14:50:40.813338751Z 172.28.0.6:52392 - "POST /events/1/reserve HTTP/1.1" 200 OK
gateway-1  | 2026-09-13T14:50:40.815971310Z HTTP Request: POST http://events:8081/events/1/reserve "HTTP/1.1 200 OK"
gateway-1  | 2026-09-13T14:50:40.819751376Z 172.28.0.1:46506 - "POST /events/1/reserve HTTP/1.1" 200 OK
payments-1 | 2026-09-13T14:53:10.997658822Z Payment success: PAY-EFF5E5AC for a919095b-828a-4bb4-b89a-3077a9e82848
payments-1 | 2026-09-13T14:53:11.001439446Z 172.28.0.6:53176 - "POST /charge HTTP/1.1" 200 OK
gateway-1  | 2026-09-13T14:53:11.003248707Z HTTP Request: POST http://payments:8082/charge "HTTP/1.1 200 OK"
events-1   | 2026-09-13T14:53:11.065580016Z Order confirmed: a919095b-828a-4bb4-b89a-3077a9e82848
events-1   | 2026-09-13T14:53:11.067820272Z 172.28.0.6:44988 - "POST /reservations/a919095b-828a-4bb4-b89a-3077a9e82848/confirm HTTP/1.1" 200 OK
gateway-1  | 2026-09-13T14:53:11.069366297Z HTTP Request: POST http://events:8081/reservations/a919095b-828a-4bb4-b89a-3077a9e82848/confirm "HTTP/1.1 200 OK"
gateway-1  | 2026-09-13T14:53:11.073437325Z 172.28.0.1:45068 - "POST /reserve/a919095b-828a-4bb4-b89a-3077a9e82848/pay HTTP/1.1" 200 OK
```

The trace can be interpreted as follows:

| Step | Service and action | Time since previous line |
|---:|---|---:|
| 1 | Events reserves one ticket and assigns the reservation ID | start |
| 2 | Events returns `200 OK` to gateway | 7.569 ms |
| 3 | Gateway records the successful events response | 2.633 ms |
| 4 | Gateway returns the reservation response to the client | 3.780 ms |
| 5 | Payments successfully charges the reservation | 150.178 s |
| 6 | Payments returns `200 OK` to gateway | 3.781 ms |
| 7 | Gateway records the successful payments response | 1.809 ms |
| 8 | Events confirms the paid reservation | 62.331 ms |
| 9 | Events returns `200 OK` to gateway | 2.240 ms |
| 10 | Gateway records the successful confirmation response | 1.546 ms |
| 11 | Gateway returns the final payment response to the client | 4.071 ms |

The observable span from the first matching reservation record to the final gateway response was approximately **150.268 seconds**. From the first gateway record for the reservation to the final gateway response it was approximately **150.257 seconds**. This unusually large value includes the manual pause between the two separate client calls that created and then paid the reservation; it is not backend processing time.

The active payment-and-confirmation part, measured from the payments success record to the final gateway response, took approximately **75.779 ms**. The current gateway access log is written when a request completes rather than when it arrives, so the exact receive-to-response duration cannot be calculated from these logs alone. A request-start event or distributed trace span would be needed for an exact end-to-end latency measurement.

## Conclusion

The lab demonstrated how image layers contribute to image size, how to inspect running containers, and how Compose provides DNS-based service discovery. The images were hardened by running all application services as a non-root user. The timestamped logs also allowed one reservation and payment to be correlated across gateway, events, and payments, while showing why explicit trace IDs are more reliable than timestamps for production observability.
