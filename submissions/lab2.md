Among the layers added by the gateway Dockerfile itself, the largest one is:

```text

```

This layer is the largest application-specific layer because it installs the Python packages and dependencies required by the gateway.

### 2.2 Container Inspection

I inspected the internal IP addresses of the three application containers:

```bash
docker inspect app-events-1 \
  --format '{{.Name}} {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'

docker inspect app-gateway-1 \
  --format '{{.Name}} {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'

docker inspect app-payments-1 \
  --format '{{.Name}} {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
```

Output:

```text
/app-events-1 172.21.0.5
/app-gateway-1 172.21.0.6
/app-payments-1 172.21.0.3
```

These are internal container addresses on the Docker network. They are different from the ports published on the macOS host.

For example:

```text
localhost:3080 → gateway:8080
```

uses a host port, while:

```text
172.21.0.6
```

is the gateway container's address inside the Docker network.

I also inspected the environment variables of the payments service:

```bash
docker inspect app-payments-1 \
  --format '{{range .Config.Env}}{{println .}}{{end}}'
```

Output:

```text

PAYMENT_LATENCY_MS=0
PATH=/usr/local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
GPG_KEY=7169605F62C751356D054A26A821E680E5FA6305
PYTHON_VERSION=3.13.15
PYTHON_SHA256=1e66a7945a48390ee4c2a4268a0e4185884059a13c4aab6d148aa208deea4a76
```

`PAYMENT_FAILURE_RATE=0.0` means artificial payment failures are disabled, and `PAYMENT_LATENCY_MS=0` means no artificial latency is configured.

The remaining variables are inherited from the `python:3.13-slim` base image.

### 2.3 Live Debugging with `docker exec`

First, I checked which user the gateway container was running as before Dockerfile hardening:

```bash
docker exec app-gateway-1 whoami
docker exec app-gateway-1 id
```

Output:

```text
root
uid=0(root) gid=0(root) groups=0(root)
```

The original container therefore ran as `root`.

#### Docker DNS configuration

I inspected `/etc/resolv.conf` inside the gateway:

```bash
docker exec app-gateway-1 cat /etc/resolv.conf
```

Output:

```text
# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 127.0.0.11
options ndots:0

# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(192.168.65.7)]
# Overrides: []
# Option ndots from: internal
```

`127.0.0.11` is Docker's embedded DNS resolver.

The gateway does not need to know the current IP address of another container. It can use the Docker Compose service name, for example:

```text
events:8081
payments:8082
```

Docker resolves these names to the current container IP addresses.

#### Gateway → events

I tested connectivity from inside the gateway to the events service:

```bash
docker exec app-gateway-1 python3 -c "
import urllib.request
print(urllib.request.urlopen('http://events:8081/health').read().decode())
"
```

Output:

```json
{"status":"healthy","checks":{"postgres":"ok","redis":"ok"}}
```

#### Gateway → payments

I also tested payments:

```bash
docker exec app-gateway-1 python3 -c "
import urllib.request
print(urllib.request.urlopen('http://payments:8082/health').read().decode())
"
```

Output:

```json
{"status":"healthy","failure_rate":0.0,"latency_ms":0}
```

Finally, I explicitly resolved the `events` service name from inside the gateway:

```bash
docker exec app-gateway-1 python3 -c \
"import socket; print('events ->', socket.gethostbyname('events'))"
```

Output:

```text
events -> 172.21.0.5
```

Using the service name is more reliable than hardcoding `172.21.0.5` because container IP addresses can change after containers or Docker networks are recreated.

### 2.6 Docker Service Discovery

The gateway finds the events service using its Docker Compose service name:

```text
events
```

Inside the gateway, DNS requests are handled by Docker's embedded DNS server:

```text
127.0.0.11
```

For this run, the lookup returned:

```text
events -> 172.21.0.5
```

Therefore, when the gateway sends a request to:

```text
http://events:8081
```

Docker resolves `events` to the current container IP `172.21.0.5`.

The service name should be used instead of the IP address because the IP can change when containers are recreated, while the Compose service name remains stable.

## Task 2 — Dockerfile Optimization

### 2.7 Add `.dockerignore`

I created a `.dockerignore` file for each application service:

```text
app/gateway/.dockerignore
app/events/.dockerignore
app/payments/.dockerignore
```

Each file contains:

```text
__pycache__
*.pyc
.git
.env
*.md
.vscode
```

Before the change, the image sizes were:

```text
app-events:latest     f4d04edbc975        272MB           61MB
app-gateway:latest    2f303dd0f727        251MB         55.7MB
app-payments:latest   e8c5206522ef        249MB         55.2MB
```

I rebuilt all application images without using the build cache:

```bash
docker compose build --no-cache
```

After adding `.dockerignore`:

```text
app-events:latest     d32043bfdfdc        272MB           61MB
app-gateway:latest    684f9f472d55        251MB         55.7MB
app-payments:latest   4ff530770146        249MB         55.2MB
```

Size comparison:

| Image          |  Before | After `.dockerignore` |
| -------------- | ------: | --------------------: |
| `app-events`   |   61 MB |                 61 MB |
| `app-gateway`  | 55.7 MB |               55.7 MB |
| `app-payments` | 55.2 MB |               55.2 MB |

The final image sizes did not change.

This is expected because the Dockerfiles already copy only specific files:

```dockerfile
COPY requirements.txt .
COPY main.py .
```

They do not use:

```dockerfile
COPY . .
```

Therefore, files such as `.git`, Markdown files, `.env`, `.vscode`, and Python caches were not copied into the image even before `.dockerignore` was added.

However, `.dockerignore` still reduced the build context.

Before the change, the gateway build showed:

```text
transferring context: 13.04kB
```

After adding `.dockerignore`:

```text
transferring context: 64B
```

This makes the build context cleaner and prevents unrelated or sensitive files from accidentally being included if the Dockerfile is changed later.

## Bonus Task — Trace a Request Across Services

To obtain clean logs, I recreated the Compose containers:

```bash
docker compose down
docker compose up -d
```

I did not use:

```bash
docker compose down -v
```

because `-v` would also remove the PostgreSQL volume.

After the restart, all three application services reached:

```text
Application startup complete.
```

I then created one reservation:

```bash
RES=$(curl -s -X POST http://localhost:3080/events/1/reserve \
  -H "Content-Type: application/json" \
  -d '{"quantity":1}')

echo "$RES"

RES_ID=$(echo "$RES" | python3 -c \
'import sys,json; print(json.load(sys.stdin)["reservation_id"])')

echo "RES_ID=$RES_ID"
```

Output:

```text
{"reservation_id":"4c7b16c4-f200-4873-b55b-ca94ef33e42b","event_id":1,"quantity":1,"total_cents":5000,"expires_in_seconds":300}

RES_ID=4c7b16c4-f200-4873-b55b-ca94ef33e42b
```

I then paid for the reservation through the gateway:

```bash
curl -s -X POST \
  "http://localhost:3080/reserve/$RES_ID/pay"
```

Output:


The purchase completed successfully.

### Bonus Timing Analysis

The trace can be correlated by the same reservation ID:

```text
4c7b16c4-f200-4873-b55b-ca94ef33e42b
```

and payment reference:

```text
PAY-F29A924F
```

Timing between observable log events:

| From                               | To                                         |      Time |
| ---------------------------------- | ------------------------------------------ | --------: |
| Events creates reservation         | Events returns reserve HTTP 200            | ~1.075 ms |
| Events reserve HTTP 200            | Gateway records reserve response           | ~2.247 ms |
| Gateway reserve response           | Gateway returns reserve response to client | ~0.710 ms |
| Payments records successful charge | Payments returns HTTP 200                  | ~0.798 ms |
| Payments HTTP 200                  | Gateway records payment response           | ~0.672 ms |
| Gateway payment response           | Events records confirmation                | ~8.626 ms |
| Events records confirmation        | Events returns confirm HTTP 200            | ~0.290 ms |
| Events confirm HTTP 200            | Gateway records confirm response           | ~0.334 ms |
| Gateway confirm response           | Gateway returns final HTTP 200             | ~0.582 ms |

From the payment success log:

```text
2026-09-13T12:19:00.313445305Z
```

to the final gateway response:

```text
2026-09-13T12:19:00.324745930Z
```

the observable payment-and-confirmation part took approximately:

```text
11.301 ms
```

The complete visible reserve-to-pay trace span from the first reservation log:

```text
2026-09-13T12:19:00.155875055Z
```

to the final gateway response:

```text
2026-09-13T12:19:00.324745930Z
```

spanned approximately:

```text
168.871 ms
```

However, this value is **not pure end-to-end service latency** because reservation and payment were executed using two separate `curl` commands.

Between the reserve response and the payment operation, the shell printed the response, Python extracted `RES_ID`, and the second `curl` process was started. The approximately `153.538 ms` gap between those log events therefore includes client-side processing.

The timestamped access logs show when the gateway finishes the request, but they do not contain a separate timestamp for when the `/pay` request first enters the gateway. To answer the exact end-to-end question, I additionally checked the gateway's built-in Prometheus request-duration metric:

```bash
curl -s http://localhost:3080/metrics | \
grep 'gateway_request_duration_seconds' | \
grep 'reserve'
```

For `/reserve/{id}/pay`, the relevant values were:

```text
gateway_request_duration_seconds_count{method="POST",path="/reserve/{id}/pay"} 1.0
gateway_request_duration_seconds_sum{method="POST",path="/reserve/{id}/pay"} 0.03850150108337402
```

Because exactly one `/pay` request was recorded after the clean restart, the histogram sum corresponds to that single request.

Therefore, the gateway end-to-end processing time for the `/pay` request was approximately:

```text
38.502 ms
```

This value measures the `/pay` request while it is processed by the gateway, including the call to `payments` and the subsequent confirmation in `events`.

## Conclusion

This lab demonstrated how QuickTicket containers operate below the application level.

The inspection showed that:

* Docker images consist of filesystem layers plus metadata history entries.
* The gateway image had 8 actual filesystem layers.
* The largest application-specific gateway layer was the `pip install` layer at `29.1MB`.
* Containers communicate through the Compose bridge network `app_default`.
* Docker's embedded DNS server at `127.0.0.11` allows services to use stable names such as `events` instead of container IP addresses.
* Container IP addresses are internal and can change when the network or containers are recreated.

The Dockerfile optimization also improved container security. Adding `.dockerignore` reduced unnecessary build context, although the final image sizes remained unchanged because the Dockerfiles already copied only specific files.

Finally, all three application containers were changed from running as `root` to running as the non-root `app` user without breaking application functionality.

The bonus trace demonstrated the complete QuickTicket purchase path:

```text
gateway → events → payments → events → gateway
```

and showed both the usefulness and the limitations of timestamp-based log correlation in a distributed system.
