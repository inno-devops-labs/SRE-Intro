### 2.6 — Docker DNS Service Discovery

Gateway connects to events using the Compose service name `events` and port `8081`. Docker Compose registers service names in its embedded DNS server at `127.0.0.11`. Inside gateway, the hostname `events` resolved to `172.21.0.5`, matching the container address from `docker inspect`.

Container IP addresses are assigned dynamically and may change after containers are recreated. Services should therefore use DNS names such as `events` and `payments` instead of hard-coded IP addresses.

### Trace Annotation

1. At `12:50:34.967132966`, events created the reservation in Redis.
2. At `12:50:34.968461841`, events returned HTTP 200 to gateway.
3. At `12:50:34.969763716`, gateway recorded the successful events response.
4. At `12:50:34.971214591`, gateway returned the reservation to the client.
5. At `12:50:35.016988883`, payments successfully created payment reference `PAY-B5E84A1B`.
6. At `12:50:35.018243841`, payments returned HTTP 200 to gateway.
7. At `12:50:35.018826591`, gateway recorded the successful charge response.
8. At `12:50:35.026075758`, events confirmed the reservation and stored the order.
9. At `12:50:35.026432133`, events returned the confirmation to gateway.
10. At `12:50:35.026794300`, gateway recorded the successful confirmation response.
11. At `12:50:35.027469550`, gateway returned the final HTTP 200 response to the client.

The observable server-side trace from the first reservation log entry to the final gateway response took approximately:

```text
12:50:35.027469550 - 12:50:34.967132966 = 60.336584 ms
```

The client-observed payment request took `26.801 ms`. The full shell scenario took `351.901 ms`, but that value also includes shell execution, temporary file handling, JSON parsing, and the time between the two separate HTTP requests.

The exact gateway request-start timestamp cannot be calculated from the current logs because gateway records an incoming request when its response is completed rather than when the request first arrives. Therefore, `60.34 ms` is the closest observable server-side duration for the complete reserve → pay → confirm sequence.
