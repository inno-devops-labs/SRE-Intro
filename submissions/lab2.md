```bash
"
```

```text
172.19.0.5
```

### How does the gateway find the events service?

The gateway finds the events service using Docker Compose service discovery. All QuickTicket containers are connected to the `app_default` network. Docker provides an embedded DNS resolver at `127.0.0.11`, allowing Compose service names to be used as hostnames.

Therefore the gateway can call `http://events:8081` instead of hard-coding a container IP address. During this run, `events` resolved to `172.19.0.5`. The container IP may change when containers are recreated, but the Compose service name remains stable.

The `.dockerignore` still reduces unnecessary build-context transfer.

## Trace analysis

| Stage | Approximate time |
|---|---:|
| Events reservation log → gateway observes reserve response | 1.56 ms |
| Gateway reserve downstream response → client response completion | 0.86 ms |
| Payments success → gateway observes payment response | 1.09 ms |
| Gateway payment response → events confirms reservation | 5.89 ms |
| Events confirmation → gateway observes confirmation | 0.75 ms |
| Gateway confirmation response → final client response | 0.57 ms |

The complete observable reservation → payment → confirmation trace spans approximately **117.16 ms**, from the first reservation log entry at `04:38:15.093517947` to the final gateway response at `04:38:15.210676528`.

The payment-and-confirmation portion from payment success to final gateway response spans approximately **8.30 ms**.

The application logs do not emit an explicit timestamp for the exact instant the gateway first receives the payment request. Therefore the exact ingress-to-response latency cannot be derived from these logs alone. The 117.16 ms figure is the total observable end-to-end sequence using the earliest reservation log and latest final gateway response.
